# Project Description  
## Fused Low-Precision GEMM for Compressed LLM Inference

**Niche:** GPU Kernel Engineering for Compressed LLM Inference

**Document type:** Project brief for external review

**Domain:** GPU systems · ML inference · CUDA / Triton kernel engineering  
**Audience:** Technical reviewers (faculty, mentors, industry)

## 1. Title

**Working title:**  
**Fused Weight-Only Low-Precision GEMM for LLM Linear Layers**  
*(W4A16-first; CUDA primary path, Triton secondary path)*

**Short name (optional):** `qgemm` / fused W4A16 GEMM

## 2. One-paragraph summary

Large language models are routinely compressed with weight-only quantization (e.g. 4-bit GPTQ/AWQ-style formats) to reduce memory and bandwidth costs. Quantizing weights alone does not guarantee proportional speedups: a naive path that dequantizes to FP16 and then calls a dense GEMM library often remains memory- or launch-inefficient. This project designs, implements, and rigorously evaluates a **fused dequantization + matrix-multiplication (GEMM) kernel path** for **INT4 weights × FP16/BF16 activations (W4A16)**, targeting shapes typical of Transformer linear layers. The primary implementation is in **CUDA C++**; a **Triton** twin validates portability of the algorithm and matches industry skill demand. Success is defined by **correctness**, **reproducible benchmarks** against strong baselines (naive dequant + cuBLAS; optionally an open high-performance kernel such as Marlin), and a **technical report** with roofline / profiler analysis—not by building a full inference server.

## 3. Motivation and problem statement

### 3.1 Context

- LLM inference cost is dominated by **memory traffic** and **matrix multiplies** in linear layers (Q/K/V/O projections, MLP).  
- **Weight-only 4-bit quantization** reduces weight footprint and HBM traffic versus FP16 weights.  
- Production stacks (e.g. vLLM quant paths, specialized kernels such as Marlin) show that **custom mixed-precision GEMM kernels** are required to approach ideal speedups.  
- There is sustained industry demand for engineers who can implement and reason about **CUDA / Triton / CUTLASS-class** kernels for **quantization and mixed precision**.

### 3.2 Problem

Given packed low-precision weights \(W_q\), scales (and optional zeros), and activations \(X\) in FP16/BF16, compute:

\[
Y = X \cdot \mathrm{dequant}(W_q)
\]

(or the layout-equivalent form used by a given linear layer), **without** a separate global-memory dequant pass that materializes a full FP16 weight matrix, when a fused path is beneficial.

### 3.3 Why this is non-trivial

- Bit-packing, group-wise scales, and layout must match efficient GPU loads.  
- Dequantization must be **interleaved** with multiply-accumulate (registers / shared memory / Tensor Core path as appropriate).  
- LLM **decode** shapes often have small leading dimensions → **memory-bound** regime; kernel design must respect roofline limits.  
- Correctness under non-ideal \(M,N,K\) and numerical tolerances is mandatory.  
- Fair comparison to baselines requires disciplined measurement (not single-shot latency).

## 4. Objectives

### 4.1 Primary objectives

1. Specify a clear **weight pack format** (document bit layout, group size, scale/zero layout).  
2. Implement a **correct** fused W4A16 GEMM (CUDA).  
3. Provide a **reference path**: dequant to FP16 + **cuBLAS** (or equivalent dense GEMM) for validation and baseline.  
4. Implement a **Triton** implementation of the same mathematical op (feature-parity as far as practical).  
5. Build a **benchmark harness** for fixed and LLM-representative \((M,N,K)\) shapes.  
6. Produce a **technical report**: methodology, results, profiler/roofline analysis, limitations.

### 4.2 Secondary objectives (time permitting)

1. Autotuning over tile sizes / launch configs for a small set of GPUs.  
2. Optional epilogue fusion (e.g. bias add) if it does not jeopardize the core GEMM story.  
3. Optional comparison against a **strong open kernel** (e.g. Marlin) on the same GPU and comparable layouts.  
4. Optional thin PyTorch binding for calling the op from Python tests.

### 4.3 Explicit non-objectives (out of scope)

| Out of scope | Rationale |
|--------------|-----------|
| Full LLM inference engine (continuous batching, paged KV, OpenAI API) | Saturated product layer; dilutes kernel contribution |
| Re-implementing vLLM / TensorRT-LLM | Not the learning or portfolio goal |
| New quantization *algorithms* (novel GPTQ/AWQ replacement) | Focus is **kernels**, not quant research |
| Multi-GPU tensor parallel / pipeline parallel | Scope and hardware dependent |
| Training kernels / backward pass | Inference-forward focus |
| Guaranteeing state-of-the-art vs Marlin on all shapes | Stretch; honest gap analysis is sufficient |
| FP8 W8A8 / FP4 as the primary v1 target | Hardware- and scope-dependent; possible future work |

## 5. Scope definition

### 5.1 In scope

- **Datatype path (v1):** W4A16 (INT4 weights, FP16 or BF16 activations, FP16/FP32 accumulation as documented).  
- **Operator:** Dense GEMM for linear-layer shapes (row-major / column-major policy documented).  
- **Languages:** CUDA C++ (required); OpenAI Triton (required twin); Python for harness/tests.  
- **Evaluation:** Correctness suite + latency/throughput + optional achieved bandwidth / Tensor utilization via Nsight Compute.  
- **Documentation:** Design notes, repro instructions, limitations, ethics/dual-use note if releasing publicly.

### 5.2 Target problem sizes

Representative **Transformer linear** shapes (exact list to be frozen after model choice), e.g.:

- Small/medium \(M\) (decode-like and modest batch).  
- Large \(K, N\) matching public 1B–8B-class models’ projection dimensions where VRAM allows.  

Microbenchmarks on synthetic \((M,N,K)\) are first-class deliverables; full end-to-end model serving is not required for v1.

### 5.3 Hardware assumptions

- Development may target consumer NVIDIA GPUs (e.g. Ampere-class laptop/desktop).  
- All claims are **device-specific**; multi-architecture portability is desirable but not a v1 gate.  
- Cloud GPU results (if any) must be labeled separately from local results.

## 6. Technical approach

### 6.1 High-level architecture

```
[Pack tool / offline layout]
        │
        ▼
 INT4 weights + scales (+ zeros)
        │
        ▼
 ┌──────────────────────────────────┐
 │  Fused kernel (CUDA / Triton)    │
 │  load pack → dequant → MMA/FMA   │
 │  → store Y                       │
 └──────────────────────────────────┘
        │
        ▼
   Activations X (FP16/BF16) → Y
```

### 6.2 Implementation stages (conceptual)

| Stage | Description |
|-------|-------------|
| **R0** | Reference: FP16 GEMM (cuBLAS) + numerical test harness |
| **R1** | Naive W4: explicit dequant buffer + cuBLAS |
| **R2** | Fused CUDA dequant-GEMM (correctness first, performance second) |
| **R3** | Optimization: vectorized loads, tiling, shared memory, optional Tensor Core / CUTLASS-inspired path |
| **R4** | Triton twin + comparative analysis |
| **R5** | Report, repro scripts, optional strong open-kernel baseline |

### 6.3 Correctness strategy

- Bitwise or tight tolerance comparison vs FP16 reference (tolerances justified for FP16/ dequant).  
- Randomized \((M,N,K)\) including awkward sizes (not only multiples of 32/64/128).  
- Fixed seeds for regression.  
- Document known numerical differences vs higher precision.

### 6.4 Performance strategy

- Warmup + multi-trial timing; report mean/median/std or multi-session ranges if noisy.  
- Baselines: (1) naive dequant + cuBLAS; (2) pure FP16 cuBLAS where meaningful; (3) optional Marlin-class open kernel.  
- Roofline: estimate arithmetic intensity of fused W4 path vs naive path.  
- Profiler: Nsight Compute counters for memory throughput / relevant pipe utilization when available.

### 6.5 Relationship to existing software

| Component | Role in this project |
|-----------|----------------------|
| **cuBLAS** | Dense FP16 baseline and post-dequant baseline |
| **Marlin (or similar)** | Study reference and optional performance ceiling |
| **CUTLASS / CuTe** | Design reference; optional use in optimized path |
| **Triton** | Second implementation language |
| **vLLM** | **Not required**; optional reading for industry context only |

## 8. Success criteria

### 8.1 Must-pass (v1 complete)

1. **Correctness:** Fused CUDA path matches reference within agreed tolerances on the frozen shape set.  
2. **Baseline win:** Clear, reproducible speedup vs **naive dequant + cuBLAS** on primary decode-like and at least one larger-\(M\) shape (magnitude depends on GPU; direction and analysis required).  
3. **Triton twin:** Exists and is evaluated (may be slower than CUDA; must be correct).  
4. **Report:** Documents method, results, profiler/roofline insight, and limitations without overclaim.  
5. **Repro:** Third party with similar GPU/CUDA stack can rebuild and run tests/benches from instructions.

### 8.2 Stretch

1. Competitive with or within a documented factor of a strong open W4 kernel on selected shapes.  
2. Autotune table for ≥2 GPU architectures.  
3. Minimal PyTorch integration for one real linear module.

### 8.3 Non-criteria (do not use as pass/fail)

- Beating TensorRT-LLM or full engine tok/s end-to-end.  
- Highest GitHub stars / product adoption.  
- Novel quant algorithm SOTA on perplexity leaderboards.
